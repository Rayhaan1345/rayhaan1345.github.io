Diabetes Risk Screening from Routine Measurements

A model and a web app built during a research internship at M42

During a research internship at M42 in Abu Dhabi, I learned how a machine-learning project runs from start to finish. I built a model that estimates diabetes risk from eight routine measurements, such as glucose, BMI and blood pressure. I then deployed it as a web app where anyone can change the inputs and get a new score. The same model also runs on this page, inside your browser.

The project follows Microsoft's Team Data Science Process, from a project charter to a feedback form for users. It was my first complete machine-learning project, and this page also notes what I would do differently now.

New to these methods? The primer builds up the ideas step by step, from a single rule to boosting, neural networks and SHAP values.

The data

The model learns from the Pima Indians Diabetes Database, a public dataset first collected by the US National Institute of Diabetes and Digestive and Kidney Diseases and shared on Kaggle. It covers 768 women of Pima heritage aged 21 or older. For a woman it records eight measurements and whether she had diabetes. Pick a measurement to compare the two groups.

Distributions from the dataset in the repository. Bars stack the women without diabetes (navy) and with diabetes (coral). Several columns use 0 for a value that was never measured, since a glucose level, blood pressure or BMI of 0 is impossible.

Explore the model

The report settles on an XGBoost model, which scored best in my tests. The repository saves a different model, a fastai neural network for tabular data, and the app runs that one. It reads six measurements as numbers, and it treats age and the number of pregnancies as categories with learned embeddings. It was trained toward 1 for women with diabetes and 0 for women without, and its output range runs from 0 to 1.2. The map shows its score for combinations of glucose and BMI.

Rebuilding the XGBoost model

The report's best model used XGBoost, a method that adds up many small decision trees. Its code is not in the repository, so the model in the next sections was rebuilt from the report's description. A search over settings found one that reproduces the report's feature-importance chart. It uses 100 trees of depth 3 and a learning rate of 0.01, trained on 80% of the data split with random seed 42.

The report counts how often the trees split on an input, which XGBoost calls the F-score. The rebuilt model matches the report on six inputs. On glucose and BMI it differs by one split, probably because of a newer XGBoost version.

Split counts in the report and in the rebuilt model. On the 154 women held out from training, the rebuilt model classifies 78.6% correctly when a score above 0.5 counts as diabetes.

Four ways to rank the inputs

Feature importance asks which inputs a model relies on. There are several ways to measure it, and they can disagree. Pick a measure to rank the inputs of the rebuilt model.

The measures agree on glucose and disagree further down. Blood pressure gets 52 splits, close to insulin and the family-history score. Yet shuffling blood pressure leaves accuracy almost unchanged, and its SHAP share is tiny. Split counts show where a model looks, and the other measures show what changes its answer.

Explain one score

A SHAP value splits the gap between the average score and one woman's score among her inputs. The idea comes from game theory, where Shapley values share a prize fairly among players. An input gets its average effect on the score, taken over all the orders in which the inputs could be revealed.

The shares add up to the score. Pick a held-out woman, or use the sliders at the top of the page.

SHAP values for the rebuilt XGBoost model, computed in your browser. The chart starts at the average score over the training data. Coral bars push the score up, toward diabetes, and teal bars push it down. The values match XGBoost's own calculation to within 0.000001.

The app

The original app runs on Streamlit Community Cloud. Sliders set the measurements, and a button returns the score. It opens with a note that it does not replace a doctor, and it links to a feedback form. It runs the same model file as the version at the top of this page.

Looking back

Looking back two years later, I would change several things. The dataset stores missing measurements as zeros: insulin is 0 for 374 of the 768 women. My model read those zeros as values, and I would now mark them as missing.

The report gives accuracy on the whole dataset, which includes the rows the model trained on. A test set kept aside from the start gives the number to trust. The model is also a regression on a yes-or-no outcome, so its score is not a calibrated probability. A classifier with a calibration check would make the score easier to read.

These lessons show up in my later work, where the evaluation is fixed before any runs.
